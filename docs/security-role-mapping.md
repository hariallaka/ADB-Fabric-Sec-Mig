# Security Role Mapping (AC3)

## Model

```
Unity Catalog SELECT grant  →  AD Group / principal (Entra object id)  →  OneLake Security Role  →  OneLake Shortcut / UCM Data Object
```

- **Unity Catalog SELECT grant** — the actual grantee of `SELECT` on a
  Databricks view, read directly from Unity Catalog
  (`information_schema.table_privileges`, or a
  `view,principal,principal_object_id,privilege` CSV for offline use). This
  is the entire "who" side of the model; nothing is cross-referenced
  against a separate identity export.
- **AD Group / principal (Entra object id)** — resolved via the Databricks
  workspace SCIM API at extraction time (`fetch_principal_directory`,
  checking Groups then Users for each grantee name) so the Entra object id
  Fabric roles require is already sitting in `extracted_grants.csv` by the
  time the Fabric-side steps run. A grantee that can't be resolved this way
  (SCIM has no match, or the extraction identity lacks SCIM read access) is
  still translated but flagged `unresolvedPrincipalObjectId: true`.
- **OneLake Security Role** — one generated per `(table, principal)` pair
  found across all extracted view definitions, named
  `role_<table_slug>_<principal_slug>` so deploys can identify and manage
  only the roles they own (see `fabric_api/deploy.py`). Carries the merged
  column list and row filter for that principal/table combination.
- **OneLake Shortcut / UCM Data Object** — the Fabric Lakehouse table (or
  shortcut) the role's `decisionRules` path scopes to. The mapping from a
  Databricks-qualified table name (`catalog.schema.table`) to a Fabric
  `(workspaceId, itemId)` is supplied out of band via a target map (see
  `tests/fixtures/deploy_targets_sample.json`).

## Group membership management

Out of scope for this toolkit by design. It never creates, edits, or
deletes an AD group or a Unity Catalog grant -- Databricks/Entra remain the
system of record for both, and this toolkit only ever reads them. Each
extraction run reflects whatever Unity Catalog's grants say *right now*, so
Fabric role membership tracks Databricks access naturally as grants change,
with no separate synchronization step to keep two systems consistent. A
grantee whose object id can't be resolved is flagged and should be blocked
from deployment until resolved (fix the SCIM lookup, or supply the id by
hand in an offline grants CSV).

## Role creation strategy

One role per `(table, principal)` combination, not one role per view. Two
views over the *same* base table, granted to the *same* principal, are
merged into a single Fabric role (their column lists and row filters are
unioned) — so Fabric role count stays proportional to the number of
distinct table/principal access patterns rather than to the number of
Databricks views.

## Relationship between Fabric roles and OneLake objects

A role's `decisionRules[].permission[].attributeValueIncludedIn` scopes it
to a path under the Lakehouse item (`Tables/<table>`), meaning a role
governs one table (or shortcut) — the first table in the view's `FROM`
clause. If a view joins multiple base tables, extraction still runs and
flags the view `is_complex`, but per-table role generation from a
multi-table view is not attempted automatically — see
[limitations.md](./limitations.md).

for visibility, but `unresolvedPrincipalObjectId: true` marks it as not
