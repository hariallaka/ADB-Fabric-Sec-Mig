# Security Role Mapping (AC3)

## Model

```
AGS  →  AD Group  →  OneLake Security Role  →  OneLake Shortcut / UCM Data Object
```

- **AGS** (AD Group Sync) stays the single, authoritative source of *who is
  in which group*. This toolkit treats an AGS export as read-only input; it
  never creates, renames, or modifies an AGS record or AD group.
- **AD Group** — resolved from the AGS export (`ags_id`, `ags_name`,
  `ad_group_name`, `ad_group_object_id`) to its Entra ID object id, which
  Fabric roles require for `microsoftEntraMembers` membership entries.
- **OneLake Security Role** — one generated per `(table, AD group)` pair
  found across all extracted view definitions, named
  `role_<table_slug>_<group_slug>` so deploys can identify and manage only
  the roles they own (see `fabric_api/deploy.py`). Carries the merged
  column and row rules for that group/table combination.
- **OneLake Shortcut / UCM Data Object** — the Fabric Lakehouse table (or
  shortcut) the role's `decisionRules` path scopes to. The mapping from a
  Databricks-qualified table name (`catalog.schema.table`) to a Fabric
  `(workspaceId, itemId)` is supplied out of band via a target map (see
  `tests/fixtures/deploy_targets_sample.json`) since that mapping is a
  workspace/environment decision, not something derivable from Databricks
  metadata alone.

## Group membership management

Out of scope for this toolkit by design — AGS is the system of record.
`mapping/role_mapper.load_ags_export()` only *reads* the latest AGS export
CSV each pipeline run, so Fabric role membership (which AD group is bound to
which role) always reflects the AD groups referenced by the current
Databricks view definitions, resolved against the most recent AGS snapshot.
If a group referenced in a view has no corresponding AGS record, the
generated role is flagged `unresolvedAdGroup: true` and should be blocked
from deployment until AGS is updated (an AGS-side action, outside this
toolkit's scope) or the view is corrected.

## Role creation strategy

One role per `(table, AD group)` combination, not one role per view. Two
views that grant different columns/rows on the *same underlying table* to
the *same group* are merged into a single Fabric role, so Fabric role count
stays proportional to the number of distinct table/group access patterns
rather than to the number of Databricks views (which can be far larger, and
often includes multiple views over the same table for different consuming
teams).

## Relationship between Fabric roles and OneLake objects

A role's `decisionRules[].permission[].attributeValueIncludedIn` scopes it
to a path under the Lakehouse item (`Tables/<table>`), meaning a role
governs one table (or shortcut). If a Databricks view spans multiple base
tables (a join), extraction still runs and flags the view `is_complex`, but
per-table role generation from a multi-table predicate is not attempted
automatically — see [limitations.md](./limitations.md).
